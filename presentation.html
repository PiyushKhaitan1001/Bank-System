01 • PROBLEM

Problem Statement & Use Case

Connect the software solution to a real user need.

Time Budget: 40s
Real-World Needs
🎯 1. What Problem Does It Solve?

Modern fintech and banking solutions are excessively reliant on bloated third-party frameworks (Spring Boot, Hibernate, external SQL engines). This induces heavy runtime memory footprints, opaque abstraction leaks, and severe supply-chain vulnerability vectors.

The Core Solution: Apex Banking proves that an industrial-grade, zero-dependency Neobank platform can be engineered purely with Core Java (JDK 17+)—utilizing native HTTP servers, custom cryptographic hashing, plain-text persistence, and clean OOP abstractions.

👥 2. Intended Users & Realistic Use Case

User Personas: Retail Banking Customers (daily financial ops) and Bank Administrators/Staff (KYC, loans, audit compliance).

  • Realistic Use Case: Customer John transfers ₹1,200 to Alice.
  • System Interaction: John logs in, enters his 4-digit security PIN. Because the transfer exceeds ₹1,000, the system triggers a 2-step simulated OTP challenge. The core engine atomistically verifies reserve balances, validates recipient existence, logs debit/credit transactions, updates expense analytics, and writes to CSV persistence.
🌐 3. Scope of the Application
  • Multi-Tier Accounts: Savings (4% p.a.), Current (₹1,000 Overdraft), Fixed Deposit (up to 8% p.a.), Recurring Deposit.
  • Transactions: Direct transfers, Instant UPI (`user@apex`), Utility Bills, Standing Instructions, FX.
  • Administration: 1-click KYC review queue, loan amortization disbursement, dispute refunds, fraud alerts.
📌 Clear Objective Statement

“To architect and implement a secure, fully-compliant Neobank Management System using strictly Core Java (JDK 17+) and OOP principles, delivering robust transaction processing and role-based administration with zero external dependencies.”

🏛 4 OOP Pillars in Production
Abstraction

Account defines abstract calculateInterest(). BankService and Storage decouple HTTP handlers from persistence.

Inheritance

SavingsAccount, CurrentAccount, FixedDepositAccount, and RecurringDepositAccount inherit core attributes from Account without duplication.

Polymorphism

Dynamic method dispatch: calculateInterest() behaves uniquely per account type. List<Account> processed uniformly during batch interest runs.

Encapsulation

All fields strictly private. Account balances can only mutate through validated deposit() and withdraw() methods.

Architectural Justification: Layered separation of concerns isolates presentation (PageBuilder), routing (BankServer), business logic (BankServiceImpl), and disk persistence (FileStorage). Modifying the UI or storage engine never invalidates core banking invariants.

Logic & Flow
🔄 Atomic Transaction Sequence Flow
[Browser Client] -- POST /transfers/send (source, target, amt, pin, otp) --> [BankServer] -- 1. Extract session cookie & resolve active User --------> [BankServiceImpl] -- 2. Authenticate 4-digit PIN via SHA-256 MessageDigest -> -- 3. If amt > ₹1,000, verify simulated on-screen OTP ----> -- 4. Check daily cumulative transfer cap (₹5,000) --------> -- 5. Query Source & Target Accounts via FileStorage ------> -- 6. Verify minimum reserve (₹500 Savings / Overdraft) ---> -- 7. Execute Atomic Mutation: withdraw() & deposit() -----> -- 8. Append 2 Transaction records to ledger --------------> [FileStorage] -- 9. Flush updated accounts & ledger to CSV on disk ------> [BankServer] <-- 10. HTTP 302 Redirect with Flash Success Banner -------

Key Logic Decision: Multi-stage atomic validation guarantees that if any precondition fails, custom exceptions roll back the process with zero balance mutation.

💻 Core Implementation Code Snippet
public synchronized void transfer(User u, String srcNum, String tgtNum, double amt, String pin, String otp) throws BankException { if (!verifyPin(u, pin)) { throw new SecurityException("Invalid 4-digit PIN."); } if (amt > 1000.0 && !verifyOtp(u, otp)) { throw new SecurityException("High-value OTP required."); } Account src = getAccount(srcNum); Account tgt = getAccount(tgtNum); if (src.isFrozen() || tgt.isFrozen()) { throw new AccountFrozenException("Account is frozen."); } src.withdraw(amt); tgt.deposit(amt); storage.logTransaction(new Transaction("TRANSFER", amt, srcNum, tgtNum)); storage.saveAll(); }

Clean execution model demonstrating custom exceptions, synchronized atomic execution, and encapsulation.
